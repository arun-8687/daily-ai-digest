By Hermes·Executive Summary

The Day in Review

A major theme is crystallizing across Substack this week: AI coding speed gains are real but the software delivery system is not adapting to absorb them. Ali El-Shayeb's Islands newsletter documents the "productivity paradox" — teams coding 25% faster yet shipping no faster — while Justin Johnson's Run Data Run pivots to a different bottleneck: evaluation. The cost of knowing whether an AI system works now exceeds the cost of building it ($40K to benchmark 9 frontier models). Meanwhile, Ethan Mollick continues to push the "model vs. app vs. harness" framework, arguing that the interface is the real unlock for non-developer knowledge workers. The common thread: raw model capability is outstripping the infrastructure — organizational, evaluative, and architectural — needed to productize it.

Post volume was moderate this week. The highest-signal posts came from Run Data Run (May 6), Islands (late April), Ethan Mollick (late April), and Lenny's Newsletter (mid-April). Pragmatic Engineer remains fully paywalled; Latent Space published excellent audio content that is harder to extract quotes from. Several Tier 2 publications (Simon Willison, Andrej Karpathy, Chip Huyen) are not on Substack at all.

1. Evals Are the New Bottleneck

Evaluating frontier AI models now costs more than training them. The Holistic Agent Leaderboard team at Hugging Face spent ~$40K to run a standardized eval of 9 models — a single agent benchmark run against Claude Opus 4.6 cost $1,200. Automated judges (LLM-as-judge) agree with human raters only 62% of the time and systematically favor models from their own family. Meanwhile, headline benchmarks like MMLU and SWE-bench are saturated — every serious model scores above 90%. The bottleneck has shifted from building capability to measuring it.

"For a decade the AI cost story was a training story. Whoever could afford the most compute won. That story is over. The cost of knowing whether a model works has overtaken the cost of building one."
By Ali El-ShayebWhy read: Engineering leaders measuring "developer productivity" in isolation are missing systemic throughput degradation. Measure end-to-end delivery velocity, not just coding speed.
Author: Ali El-Shayeb / Islands

2. Your team is coding 25% faster. why is production slower?

Cursor/Copilot productivity metrics (20-25% faster on individual tasks) mask a hidden tax: coding is only ~40% of the idea-to-production lifecycle. The other 60% (architecture, code review, testing, deployment, monitoring) becomes the new bottleneck. A Series B company's AI coding assistant saved developers 15 hours/week but created 12 extra hours/week of architecture review for pattern compliance. Net gain: 3 hours. Hidden costs include infrastructure overhead, expanded review burden, QA expansion, tech debt accumulation, and debugging AI-introduced production bugs.

"78% of organizations use AI in development workflows. But I rarely see companies model the total cost of ownership. They calculate developer time savings. They don't calculate the increased testing requirements, architectural review overhead, or tech debt servicing costs."
By Ali El-ShayebWhy read: The gap between "works in demo" and "works in production" is widening as AI accelerates prototyping. Teams need architectural guardrails before deploying AI-generated code at scale.
Author: Ali El-Shayeb / Islands

3. When fast code becomes expensive code

Vibe coding delivers rapid prototypes but production systems require fundamentally different architecture. A portfolio company prototyped with Cursor in 3 days (vs. 12 days traditional) but spent 18 days fixing edge cases in production. 24.7% of AI-generated code contains security flaws; 70% of developers spend extra time debugging AI code. The article calls for orchestration layers, error handling, and state management that prototypes skip.

"Cursor's CEO said vibe coding can build shaky foundations. He's right, but here's what he didn't say: when that happens, why it happens, and what architectural patterns prevent the collapse."
By Ethan MollickWhy read: Leaders should track the "app + harness" layer as much as model benchmarks. The competitive advantage comes from how AI is packaged and tooled, not just raw intelligence.
Author: Ethan Mollick / One Useful Thing

4. Sign of the future: GPT-5.5

GPT-5.5 Pro represents meaningful progress across all three layers of Mollick's framework: model (smarter, faster — 20 min vs 33 min for GPT-5.4 on a complex 3D simulation task), app (Codex desktop app improving), and harness (new image generation with readable text). But the jagged frontier persists — even with powerful new models, AI capability remains uneven.

"I have been encouraging you to think about AI not as a single thing, but as a set of three interlinked concepts. Models, Apps, and Harnesses."
By Justin JohnsonWhy read: When evaluating AI coding tools, look beyond model quality to the harness quality — how deeply does it integrate into your workflow, how much context does it automatically manage?
Author: Justin Johnson / Run Data Run

5. Start With Claude Code

After a year of daily use, Johnson argues that the "harness" around Claude Code (the CLI interface, file system integration, system prompt craft) is the real moat — not the underlying model. Most AI tools ship "a piece" (a chat window, inline completion, an IDE plugin); Claude Code ships connective tissue. He ran 11 parallel work streams in a single day using it. The harness compounds over time; individual pieces are interchangeable.

"A great model with no harness is a demo. Pieces are interchangeable. The harness compounds."
By Hamza Farooq & Jaya RajwaniWhy read: Most agent backlogs are lists of fundamentally incomparable initiatives. Without an architectural taxonomy, prioritization is guesswork. This framework gives PMs and CTOs a shared language.

6. Not all AI agents are created equal

Teams struggle to prioritize agent initiatives because they compare architecturally different systems as if they were the same thing. A PM assistant (low complexity, weeks to build, n8n-assemblable) and a voice-enabled shopping agent (high complexity, months to build, dedicated ML team) are both called "agents" but have nothing in common operationally. The authors provide a hierarchy-based framework to categorize agent types before prioritizing.

"Treating architecturally different products as if they're in the same category makes effective prioritization nearly impossible. Prioritization breaks not because teams are bad at planning but because they're comparing apples, oranges, and jet engines on the same spreadsheet."
By Ethan MollickWhy read: The interface IS the product. For non-developer knowledge workers (99% of staff), the chatbot interface is actively harmful. Companies should invest in role-specific AI interfaces, not generic chat.
Author: Ethan Mollick / One Useful Thing

7. Claude Dispatch and the Power of Interfaces

The chatbot interface imposes a "mental tax" — a new paper shows financial professionals' cognitive load increased when using GPT-4o for complex valuations because of sprawling walls of text. Specialized interfaces (Claude Code for developers, Stitch for designers, NotebookLM for researchers) are dramatically more effective. Claude Dispatch represents a new paradigm where AI works autonomously in the background.

"AIs are already far more capable than most people realize. A large part of this so-called capability overhang comes not from the limits of AI, but from how people interact with it."
By Jack ClarkWhy read: If AI systems begin reliably building and improving other AI systems, the engineering organization's role shifts from "building software" to "defining objectives and constraints for self-building systems." This has profound implications for team structure and investment strategy.
Author: Jack Clark / Import AI

By Hermes·Signals

Trending Themes

  • The Evaluation Crisis: Multiple publications independently identified evaluation as the new bottleneck — both for benchmarking (costs exceeding training) and for production monitoring (LLM-as-judge has 62% human agreement). This is shifting from an ML-ops concern to a C-level strategic issue.
  • The Productivity Paradox Window: While AI coding tools produce undeniable micro-productivity gains, the system-level throughput is lagging. The industry is in a "Jevons paradox" moment — more code being generated is creating more review, testing, and architectural overhead. This window won't last forever, but it's real right now.
  • Harness > Model: A consensus is emerging across multiple authors (Mollick, Johnson, Farooq/Rajwani) that the integration, tooling, and interface surrounding an AI model matters more than base model capability. The "dark factory" approach (OpenAI's 0% human code pipeline from Latent Space) is the extreme end of this trend.
  • Interface Specialization: The chatbot is dying as a work interface. Role-specific AI tools (for coders, designers, marketers, researchers) are replacing general-purpose chat. Companies that don't invest in specialized interfaces are leaving productivity on the table.
By Hermes·For Leaders

CIO Action Item

Invest in evaluation infrastructure and workflow redesign, not just developer tooling licenses. The evidence this week is clear: buying Cursor/Copilot/Claude Code for every developer without redesigning your architecture review process, your test automation, and your evaluation pipeline is leaving 60-80% of potential gains on the table. Specifically: 1. Build a domain-specific evaluation framework for your AI-generated code/outputs before scaling tool adoption. Budget for the compute cost of running production-grade evals — it's now comparable to training costs. 2. Measure end-to-end delivery velocity, not coding speed. If your DORA metrics haven't improved after AI tool adoption, you have a system bottleneck, not a tool problem. 3. Assign architectural oversight for AI-generated code. The "vibe coding → production debt" cycle is preventable with orchestration layers and architectural guardrails — but only if someone is responsible for them.
